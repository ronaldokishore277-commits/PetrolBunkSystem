# Automated Fuel Management System

A desktop-based petrol bunk/fuel station management **simulation** built with Java Swing and MySQL. The application presents a live dashboard and simulates four fuel pumps operating concurrently.

## Project overview

The application demonstrates:
- Java Swing desktop GUI development.
- Multithreading with a fixed-size Java executor.
- Synchronization to protect shared fuel tank inventory.
- JDBC connectivity to a MySQL database.
- Transaction recording and shift settlement.
- Live dashboard updates, KPIs, progress, tank gauges and a pump revenue chart.

> **Scope note:** This project simulates pump activity. It does not connect to real fuel dispensers, payment terminals, sensors or physical pump hardware. Transaction litres and timing are generated by the simulation.

## Implemented modules and functionality

### 1. Shift configuration
- Operator name and access-level fields are displayed.
- Petrol and diesel prices per litre can be entered.
- Operating expenses can be entered.
- Input validation rejects non-numeric or invalid rates and negative expenses.
- The **START SHIFT** button begins a simulation.

### 2. Fuel tank management
- Separate Petrol and Diesel tank models.
- Each tank starts at a configured capacity of 10,000 litres for each shift.
- Synchronized fuel deduction prevents concurrent pump tasks from overdrawing the same in-memory tank.
- Updated tank volumes are written to MySQL when a database connection is available.
- Dashboard tank gauges display the simulated inventory.

### 3. Multi-pump simulation
- Four simulated pumps: Pump P1, Pump P2, Pump D1 and Pump D2.
- P1/P2 use the Petrol tank; D1/D2 use the Diesel tank.
- A fixed thread pool of four worker threads runs pump jobs concurrently.
- Five jobs are submitted for each pump (20 scheduled jobs in total).
- Each job simulates a short delay and a randomly generated fuel volume.

### 4. Transaction processing
- A transaction receives a generated eight-character ID.
- The application calculates sale value using volume multiplied by the configured fuel rate.
- Transaction details include time, ID, pump, fuel type, litres and amount.
- Transactions are displayed in the live transaction table.
- Transaction rows are inserted into MySQL when the database is available.

### 5. Live dashboard and analytics
- Gross revenue KPI.
- Total litres dispensed KPI.
- Completed transaction count and progress.
- Net profit KPI.
- Petrol and Diesel inventory gauges.
- Revenue-by-pump bar chart.
- Live date and time.
- Shift status and database status indicators.

### 6. Shift settlement
- Gross collections are calculated from completed simulated transactions.
- Net profit is calculated as gross collections minus operating expenses.
- A shift settlement record is inserted into MySQL when the database is available.
- An end-of-shift summary is displayed.

### 7. Database/demo mode
- The application attempts to connect to MySQL when it performs a database operation.
- If the database is unavailable, the UI continues in demo mode and indicates that data was not saved.
- Demo mode is not a replacement for database persistence.

## Requirements / dependencies

Install the following before running:
1. **JDK 17 or later** (JDK 17 or 21 recommended).
2. **MySQL Server 8.x**.
3. **Apache Maven 3.8+**.
4. An IDE is optional. IntelliJ IDEA, Eclipse or NetBeans can open the Maven project.
5. MySQL Connector/J is downloaded automatically by Maven from the dependency declared in `pom.xml`. You do not need to copy a connector JAR into the repository manually.

Check installations:

```bash
java -version
javac -version
mvn -version
```

## Database setup

1. Start the MySQL server.
2. Open MySQL Workbench or a MySQL terminal.
3. Open and execute `database/petrol_bunk.sql`.
4. The script creates the `petrol_bunk` database and the required tables:
   - `tanks`
   - `transactions`
   - `shift_settlements`
5. It inserts the Petrol and Diesel tank rows. These rows are needed because the application updates tank records by `fuel_type`.

You can verify the setup with:

```sql
USE petrol_bunk;
SHOW TABLES;
SELECT * FROM tanks;
```

## Configure database credentials

The source code does not contain a real database password. The application reads these environment variables:

| Variable | Default | Purpose |
|---|---|---|
| `DB_URL` | `jdbc:mysql://localhost:3306/petrol_bunk` | JDBC connection URL |
| `DB_USER` | `root` | MySQL username |
| `DB_PASSWORD` | empty | MySQL password |

### Windows PowerShell

Set these values in the same PowerShell window before starting the app. Replace the example password with the password configured on your own MySQL server:

```powershell
$env:DB_USER = "root"
$env:DB_PASSWORD = "YOUR_MYSQL_PASSWORD"
$env:DB_URL = "jdbc:mysql://localhost:3306/petrol_bunk"
```

Do not commit your actual password, `.env` file, or other credentials to GitHub.

## Build and execute

Open a terminal in the repository root (the folder containing `pom.xml`).

### 1. Compile and package

```bash
mvn clean package
```

### 2. Run the desktop application

```bash
mvn exec:java
```

On the dashboard:
1. Enter the operator name.
2. Enter Petrol and Diesel rates.
3. Enter operating expenses.
4. Click **START SHIFT**.
5. Observe the transaction feed, KPIs, tank gauges, pump chart and progress.
6. Review the end-of-shift settlement summary.

If MySQL is not configured or reachable, the simulation can still run in demo mode, but records will not be persisted.

## Database verification after a shift

Run these queries in MySQL Workbench:

```sql
USE petrol_bunk;

SELECT * FROM transactions ORDER BY created_at DESC;
SELECT * FROM tanks;
SELECT * FROM shift_settlements ORDER BY settled_at DESC;
```

## Current implementation notes

- Pump activity and fuel volumes are simulated and randomized.
- Each new shift initializes the in-memory tank models at 10,000 litres. The current application writes tank levels to MySQL but does not load the previously stored tank levels when a new shift starts.
- Database errors switch the displayed status to offline/demo mode; the current implementation does not queue failed writes for later retry.
- The application uses the configured operating expenses as a shift-level deduction from gross collections. Net profit here is a simplified project calculation, not a full accounting statement.
- The access-level field is displayed as shift configuration; this source does not implement user authentication or role-based authorization.
